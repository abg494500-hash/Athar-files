# معالجة ثغرات npm الإحدى عشرة — الحالة، والمطلوب، وخطة آمنة (r24)

> **صدق أولًا:** وصلني العدد (11: 8 متوسطة، 1 عالية، 2 حرجة) **دون محتوى التقرير**، وبيئتي بلا سجل npm (`npm view` لا يردّ). لذلك **لم أحدّد الحزم ولا الإصدارات التي تصلحها، ولم أعدّل أي اعتمادية** (لا `package.json` ولا القفل). تحديد «الإصدار الذي يصلح الثغرة فعلًا» يحتاج بيانات السجل؛ التخمين من الذاكرة غير مقبول لأن قاعدة الثغرات تتغير يوميًا وتاريخ اليوم بعد حدود معرفتي. ما فعلتُه: أدوات تجعل الخطوة التالية دقيقة وقابلة للتحقق، واكتشاف مشكلة حقيقية في القفل (§2).

## 1) ما أحتاجه منكِ (ملفان فقط)
في PowerShell داخل `athar`:
```
Copy-Item package.json package.backup.json
Copy-Item package-lock.json package-lock.backup.json
npm audit --json > audit.json
npm audit --omit=dev --json > audit-prod.json
node --experimental-strip-types --no-warnings scripts/summarize-npm-audit.mjs audit.json > audit-summary.md
```
أرسلي لي: **`audit.json`** (أو `audit-summary.md`) و**`package-lock.json` الحالي من جهازكِ** و`package.json`. (لا تنفّذي `npm audit fix`.)

## 2) اكتشاف: قفل الحزمة المُسلَّمة غير متّسق مع `package.json`
`package.json` يطلب `@types/node ^22.10.0` (مباشرة، تطوير) **وليس له أثر في `package-lock.json` الذي في حزمتي** (القفل لا يذكره إطلاقًا). كنتُ أطلب منكِ `npm install` (لا `npm ci`)، فمن المرجّح أن `npm install` عندكِ **أضاف `@types/node` وأعاد كتابة قفلكِ المحلي**. النتائج:
- تقرير `npm audit` الذي أجريتِه يخص **قفلكِ المحلي المُعدَّل**، لا القفل الذي في حزمتي؛ فأي تحليل لقفلي قد يختلف عنه (وقد تكون إحدى الثغرات في `@types/node`/`undici-types` المضافتين).
- `npm ci` على حزمتي سيفشل لعدم الاتساق. **لا تستبدلي قفلكِ المحلي بقفل الحزمة** وأرسلي لي قفلكِ لأدمجه في r25.
- حارس جديد يكتشف هذا آليًا: `node scripts/check-dependency-policy.mjs` (على حزمتي يفشل بند «القفل متّسق مع package.json» ← `@types/node`، وهذا المتوقع إلى أن أستلم قفلكِ؛ وعلى قفلكِ المحلي المتّسق يجب أن ينجح).

## 3) الأدوات الجديدة (كلها محلية، بلا شبكة، لا تعدّل شيئًا)
| الأداة | وظيفتها |
|---|---|
| `scripts/summarize-npm-audit.mjs` (موسَّعة) | من `audit.json` + القفل: لكل حزمة الخطورة، **إنتاج/تطوير**، مباشرة/متعدّية، **الإصدار المثبَّت**، **مسار الاعتماد** من القفل، هل الإصلاح **كاسر**، وعنوان الثغرة ورابطها؛ وقسم «أوامر مقترحة» لغير الكاسر فقط: مباشرة ⇒ `npm install الحزمة@الإصدار`، متعدّية ⇒ `npm audit fix --dry-run` (**لا** `npm install` لمتعدّية لأنه يحوّلها إلى مباشرة في `package.json`). |
| `scripts/dependency-paths.mjs <حزم>` | مسارات الاعتماد ومن يطلب كل نسخة مثبَّتة وبأي نطاق، من القفل فقط. |
| `scripts/check-dependency-policy.mjs` | يمنع: **أي رفع major** لحزم خط الأساس (`docs/dependency-baseline.json`: React/React Router/Vite/Vitest/esbuild/rollup/TypeScript/Tailwind/jsdom/supabase-js…) دون `--allow-major=<حزمة>`؛ قفز نطاق مباشر بـmajor؛ اعتمادية مباشرة جديدة؛ قفل غير متّسق؛ حزمة من خارج `registry.npmjs.org` أو بلا `integrity`؛ `overrides` غير موثَّقة. يعرض حزم سكربت التثبيت للمراجعة. |
تُختبر هذه الأدوات بـ25 اختبارًا (قفل تركيبي بكل الحالات + مشاريع مؤقتة)، وأمسكت طفرات عمدية.

## 4) خطة المعالجة بعد استلام التقرير (أقل تحديثات متوافقة)
1. **تصنيف:** عالية/حرجة أولًا، ثم الإنتاج قبل التطوير (`audit-prod.json` يحدّد ما يُشحن للمتصفح).
2. **لكل حزمة، التحقق من أن الإصدار المقترح يصلحها فعلًا:** `npm view <حزمة>@<إصدار> version` (موجود؟)، ثم `npm audit fix --dry-run` (ما سيتغير في القفل بلا تنفيذ)، ثم بعد التطبيق **إعادة `npm audit`**: الثغرة يجب أن تختفي من التقرير (الدليل الوحيد المقبول).
3. **غير الكاسر فقط** (`fixAvailable.isSemVerMajor: false`) يُطبَّق، على نسخة احتياطية، حزمةً حزمةً أو دفعة صغيرة: `npm install ...` أو `npm audit fix` **بلا `--force`**، ثم: `node scripts/check-dependency-policy.mjs` (يجب ألا يظهر major جديد) → `npm run typecheck` → `npm test` → `npm run build` → `npm audit`.
4. **الكاسر** (أي major لـReact Router أو Vite أو Vitest أو غيرها): **لا يُنفَّذ.** أحلّله أولًا (§5) وأقدّم خطة انتقال، وتوافقين، ثم يُنفَّذ على فرع/نسخة منفصلة بـ`--allow-major=<الحزمة>`.
5. **لا استثناءات تخفي الثغرات** (لا `overrides` ولا `audit-level` ولا تجاهل). إن تعذّر الإصلاح: أشرح السبب والخيارات والمخاطر وأطلب قراركِ، وتُسجَّل في `DECISIONS_LOG.md` بتاريخ مراجعة.
6. بعد كل دفعة: ZIP جديد، وتحديث خط الأساس **بقرار مقصود فقط** (`--write-baseline`).

## 5) إن احتاج الإصلاح تحديثًا رئيسيًا: أسئلة التحليل (لم أجب عنها لأنها تحتاج التقرير والسجل)
| الحزمة (المثبَّت الآن) | ما يجب التحقق منه قبل أي رفع |
|---|---|
| `react-router-dom` / `react-router` 6.30.6 (**إنتاج**) | هل الثغرة قابلة للاستغلال في تطبيقنا (SPA بـHashRouter بلا SSR)؟ ما الإصدار الأدنى المصلِح؟ خريطة تغيّرات الواجهة من 6 إلى 7 (التسمية والحزم وأعلام `future`)، وأي مسار في `App.tsx` وحارس `Guard` والاختبارات يتأثر؟ هل تدعمه نسخة React المثبَّتة؟ |
| `vite` 5.4.21 / `vitest` 2.1.9 / `vite-node` / `esbuild` 0.21.5 / `rollup` (**تطوير**) | هذه السلسلة مترابطة (vitest يحدّد نطاق vite المدعوم). هل الثغرات في خادم التطوير/الأدوات فقط (فلا تدخل الموقع المنشور)؟ أصغر مجموعة إصدارات متوافقة معًا تصلحها؟ توافق `@vitejs/plugin-react` و`vite-plugin-singlefile` و`jsdom` وإصدار Node المطلوب؟ |
| `@supabase/supabase-js` 2.118.0 (**إنتاج**) | عادةً تحديث ثانوي؛ التحقق من سجل التغييرات وأن `createClient`/المصادقة لم تتغير. |
أي رفع يمرّ بـ`check-dependency-policy --allow-major=...` وبمجموعة الاختبارات كاملة وبناء الواجهة، ويُقاس حجم الحزمة (تحذير حجم JavaScript الحالي معلوم، وليس ثغرة).

## 6) ما لا أستطيع ضمانه
أن التحديثات غير الكاسرة لن تغيّر سلوك الاختبارات أو البناء عندكِ؛ هذا يُثبت بتشغيلكِ الأوامر أعلاه فقط. وأن الثغرات «المتوسطة» الثماني ليست قابلة للاستغلال في سياقنا: لا يُحكَم قبل رؤية كل واحدة.
