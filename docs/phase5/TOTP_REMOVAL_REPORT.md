# إلغاء التحقق بخطوتين (TOTP) للمالكة والمديرة — تقرير الدفعة (A-98، 0.6.7، حزمة r16)

> **الطلب (2026-10-23):** إلغاء TOTP والتحقق الإضافي للمالكة والمديرة، مع الإبقاء على البريد المسجَّل وكلمة المرور الصحيحة وصلاحيات الدور ومنع الدخول غير المصرَّح. لا تعديل على Supabase الحقيقي ولا تشغيل SQL عليه.
> **الحالة بصدق:** الكود والاختبارات الوهمية والفحوص الساكنة نُفِّذت فعليًا (القسم 5). **SQL الجديد لم يُشغَّل على أي PostgreSQL** (لا PostgreSQL في بيئتي) ولا على Supabase. **لم يُجرَّب دخول حقيقي.**

## 1) ما الذي يحكم الدخول الآن
الدخول المصرَّح (`authorized`) يتطلب **كل** ما يلي، وأي خلل يعني رفضًا وخروجًا محليًا (فشل مغلق):
1. بريد مسجَّل في Supabase Auth وكلمة مرور صحيحة (`signInWithPassword`).
2. `getUser()` من الخادم (لا الاكتفاء بالجلسة المخزَّنة).
3. صف **نشط** للمستخدمة في `staff_profiles` بدور `owner` أو `director`.
4. تأكيد الدور من الخادم عبر `current_staff_role()` ومطابقته لصف الجدول (null أو تعارض ⇒ رفض).
5. في قاعدة البيانات: سياسات RLS ودوال الأدوار تعتمد على `current_staff_role()` وحدها؛ مستخدمة بلا صف نشط لا ترى شيئًا ولا تكتب شيئًا، والتعطيل بـ`is_active=false` يسحب الدور فورًا.
لم يتغير: رسالة الرفض العامة (لا تكشف وجود الحساب)، حدّ 429، الأعطال المؤقتة (`check_failed` دون محو الجلسة)، الخروج المحلي، فصل صلاحيات المديرة عن المالكة، إنشاء الحسابات عبر `bootstrap_staff` فقط.

## 3) الاختبارات الجديدة في SQL (`tests/sql/25_staff_accounts_005.sql`) — غير مُشغَّلة
تعريف الدالة بلا `aal|jwt`؛ المالكة بكلمة المرور وحدها تعمل بدورها؛ المديرة بدورها (لا سجل عمليات)؛ مستخدمة غير مسؤولة ومعرّف مجهول: لا دور ولا بيانات؛ لا إدراج ذاتي ولا تنفيذ `bootstrap_staff`؛ حارس الجدول وقواعد `bootstrap_staff`؛ **التعطيل بـ`is_active` يسحب الدور وإعادة التفعيل تعيده**. تُشغَّل محليًا عبر `tests/sql/run-sql-tests.*` (بعد إضافتها للمشغّل — انظر القسم 6) وعلى Supabase عبر `02_security_check.sql` المولَّد.

## 4) مخاطر يجب أن تعرفيها (قرارك مقبول، لكن بوضوح)
- المالكة تملك صلاحيات واسعة (تنزيل الأرشيف، الحذف الآمن، سجل العمليات). صار **أمان الحساب** معتمدًا على كلمة المرور وحدها: سرقتها أو تخمينها أو إعادة استعمالها من موقع آخر تعني دخولًا كاملًا. لا يوجد ما يحمي بعدها إلا RLS.
- **توصيات بلا كلفة:** كلمة مرور طويلة فريدة (مدير كلمات مرور)، تعطيل التسجيل الذاتي (موثَّق)، إبقاء حدّ المحاولات في Supabase Auth، وتفعيل «حماية كلمات المرور المسرَّبة» وحدّ أدنى للطول إن كانت متاحة في خطتكِ المجانية (**لم أتحقق من توفرها**؛ أرسلي لقطة إعدادات Auth).
- كلمة مرور المديرة تُغيَّر من لوحة Supabase بيد المالكة (قرار سابق)، ولا شاشة «نسيت كلمة المرور».
- تحذير تشغيلي: سرقة رمز الجلسة (JWT) لم تعد محصورة بمن يملك الرمز الثاني؛ مدة الجلسة الافتراضية في Supabase هي الحد.

## 5) ما اختُبر فعليًا (بيئتي: Linux، Node 22، بلا شبكة ولا PostgreSQL ولا vitest)
- مشغّل Node البديل: **153/153** (قبل التعديل 158؛ في `auth.test.ts` حُذفت 9 اختبارات TOTP وأُضيفت 4: دخول مباشر بعد تأكيد الدور، غياب أي حالة/استدعاء MFA، ترتيب التأكيد قبل أي جلب بيانات، رفض عند null من الخادم بعد عطل. تعديلات `release-gate` و`login.ui` خارج نطاق هذا المشغّل ولم تُنفَّذ). اختبار طفرات: إزالة مطابقة الدور ⇒ 3 إخفاقات؛ إزالة فحص الصف النشط ⇒ 4 إخفاقات.
- فحص SQL الساكن **39/39** (طفرة بإضافة aal إلى 005 أسقطت 4 فحوص ثم أُعيد الملف)، وفحص المرحلة 3 الساكن **30/30**.
- `tsc --strict` نظيف على `controller.ts` و`fakeBackend.ts` و`types.ts`؛ فحص صياغة بلا أخطاء على `Login.tsx` وملفات الاختبار المعدّلة.
- **لم يُشغَّل:** `vitest` الكامل (اختبارات الواجهة `login.ui.test.tsx` وغيرها عُدّلت ولم تُنفَّذ)، `npm run typecheck`/`build` الكاملان، أي SQL، أي دخول حقيقي. `review/athar-ui-review.html` **لم يُعاد بناؤه** (يحوي نصًا قديمًا عن TOTP في الحزمة المضمّنة فقط).

## 6) ما يلزم منكِ على Windows (بالترتيب، لا حاجة لخدمة حقيقية)
1. فك الـZIP، افتحي PowerShell داخل `athar`.
2. `npm install` (لا `npm ci`) ثم `npm run typecheck` ثم `npm test` وأرسلي النتيجة كما هي.
3. `node scripts/check-sql-static.mjs` و`node scripts/check-stage3-static.mjs` (يجب 39/39 و30/30).
4. (اختياري، يحتاج PostgreSQL 15+ محليًا) `tests\sql\detect-postgres.ps1` ثم المشغّل. **ملاحظة:** المشغّلات الحالية تشغّل 10 و20 فقط؛ ملف `25_staff_accounts_005.sql` لم يُضف إليها بعد (يُضاف في دفعة SQL المحلية عند توفر PostgreSQL).
